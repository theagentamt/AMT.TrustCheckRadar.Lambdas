# SECUR4ALL-333: disabled verified-support deletion admission candidate

Follow-up: [supervised shared-inbox verifier](support-deletion-human-verifier.md)
records the subsequently approved email-confirmation, same-case 30-day retention
and same-owner/separate-role choices. The original candidate boundary below is
historical; these choices do not imply deployed signer access or mailbox retention.

This is engineering preparation for SECUR4ALL-92's owner-approved verified-email
fallback. It is not an operational fallback yet. The code cannot determine that an
email sender owns an account, mint a verification record, or select the missing
ownership-verification/support-case retention policy. No support route, signer,
KMS key, operator grant, records, customer deletion or deployment is created here.

## Trust and request contract

Package `support_account_deletion.zip`, Python 3.14 ARM64, handler
`app.lambda_handler`. `SUPPORT_ACCOUNT_DELETION_ENABLED` defaults closed. Anything
other than exact `true` returns fixed HTTP 503 `SUPPORT_ADMISSION_DISABLED` before
loading the runtime or initializing an AWS client. It does not dispatch stream,
scheduled reconciliation or public user-JWT events. Enabled failures expose only
503 `SUPPORT_ADMISSION_UNAVAILABLE`, without logging bodies, identities, signatures,
support evidence or provider exception text.

The proposed private operator route is HTTP API payload 2.0,
`POST /support/account-deletion`, with **AWS_IAM** authorization. The code matches
API/account/stage/route/function, the assumed-role ARN and immutable role ID from
`requestContext.authorizer.iam`. Ordinary headers/body actor claims and JWT claims
are not principals. Actual deployed gateway event shape remains to be qualified.
The context is trustworthy only with the separately audited invocation boundary:
the operator and signer must not have direct Lambda Invoke permissions (including
inherited policies/permissions boundaries/session grants). A resource-policy Allow
for API Gateway is not a Deny of other identity-based invocation. No function URL
or second invocation path may bypass this boundary. Signer and operator are
separate authorities; operator has no KMS Sign and signer cannot submit/invoke.

The request is canonical ASCII JSON (`sort_keys`, compact separators, ASCII
escaping) with exactly `record` and `signature`. No duplicate/unknown keys or
noncanonical body/base64 encoding is accepted. The record's closed fields are
defined in `src/support_account_deletion/contract.py:RECORD_FIELDS`. It binds:

- Purpose/version, Dev environment, AWS account/region, API/stage/route/function.
- Exact permitted operator role ARN and immutable role ID.
- Independently approved verification-policy digest, readiness digest and global
  revocation generation; these are pins, not assertions generated by the caller.
- Exact Cognito pool/sub (canonical UUID including UUIDv7), stable original
  UUIDv4 operation, and SHA256 of the observed supported profile fields.
- Separate request-received, ownership-verified, issued and expiry epochs.
  No future or nonintegral clocks; the explicit configured freshness cap is at
  most 300 seconds and has no enabled default. Freshness applies to ownership
  verification, not the original mailbox receipt: an older request can be verified
  now. This engineering ceiling does not approve an operational validity policy
  or set a five-minute support-response SLA.

Signature is RSA_3072 / `RSASSA_PSS_SHA_256`, over the canonical record bytes, using
KMS `Verify` with `MessageType=RAW` and the exact pinned key ARN. No key alias,
caller-selected algorithm or alternate signing key is accepted. `SignatureValid`,
returned key ARN and returned algorithm must all match. The implementation never
calls Sign, CreateKey, GetPublicKey, credential reset, user-authentication or
AdminDeleteUser. A mocked/locally signed test record is not ownership evidence.

## Admission, races and replay

The entire capability and current configuration are checked before reading any
existing command, including replay. Strong users/ledger table identity and
approved twelve-component inventory checks precede admission. For first admission,
the current owned ACTIVE or PENDING_AGE_GATE profile must match the signed hash;
Cognito username/sub and current name/email/phone snapshot must agree. These
checks detect stale identity state, not ownership of a mailbox. Unknown profile
fields fail closed. Equality for every observed supported field, and absence for
unobserved supported fields, is merged into the existing profile Update CAS.

`AccountDeletionService.request` then creates its unchanged atomic profile fence,
fixed account-deletion command, campaign recovery control/job and inventory check.
No new receipt is issued by this adapter. Existing streams/reconciliation and the
twelve-component finalizer remain responsible for session, owned-data and identity
cleanup. No device/phone reinstall, user password or fabricated `auth_time` is used.
The only shared-service edit makes its existing error import work both as a
package and as the existing flat Lambda module.

An exact existing original command can acknowledge admission while the capability
is still valid, without a surviving profile or Cognito user. This does not certify
all-component completion: response always says `completionVerified:false`.
Different operations, expired proof, changed pins/generation and malformed terminal
records refuse. Clocks/deadlines never refresh. One transaction attempt only;
lost acknowledgment triggers read-only exact-command reconciliation, never a write
retry. If expiry, budget or a read failure prevents acknowledgment, the result is
unconfirmed even if a command committed. Operators must observe that same original
operation; do not sign a replacement operation to turn uncertainty into success.

Every further SDK call is guarded by monotonic integral time, signed validity and
at least 6,000ms remaining. An external call can still complete after expiry; the
following check refuses success. This is not transactional revocation across KMS,
Cognito and DynamoDB. Configuration generation revokes future checks globally;
there is no individual capability revocation store. Old invocations must be drained
when revocation/activation configuration changes.

## Configuration and future least-privilege permissions

Only the disabled boolean is needed for closed infrastructure preparation. Enabled
configuration requires `SUPPORT_ACCOUNT_DELETION_CONFIG_JSON` with exactly the
fields in `contract.py:CONFIG_FIELDS`; there are no invented policy/table/key pins.
It is Dev-only, with one to ten exact subjects. The two table IDs and ARNs must
match live DescribeTable results. The fixed inventory digest/revision must validate
all twelve components. The signed readiness hash is an externally reviewed
deployment snapshot, **not** a live check of every worker/IAM/scope/stream. Deployment
qualification must prove all downstream scopes include each allowed subject and
keep that evidence current. Merely matching arbitrary digests is not approval.

Future role permissions needed (none deployed by this source change):

- KMS Verify on one independently provisioned asymmetric signing key; no Sign.
- Cognito AdminGetUser on the exact pool; no password/reset/auth/delete action.
- DynamoDB DescribeTable on exact users and ledger; strong GetItem on users
  PROFILE and ledger inventory/account keys; Query on the owned ACCOUNT recovery
  job prefix.
- Transaction-only Update of users PROFILE; Put of ledger deletion command and
  recovery job/control; Update of existing recovery control; ConditionCheck on
  the exact account-data inventory and existing recovery receipt guard.
- No standalone item writes, verification table, receipt writer, inventory writer,
  account eraser, queue operation or privilege to change its configuration.

See the unchanged source transaction for exact action/leading-key qualification.
DynamoDB IAM leading keys cannot restrict a sort key by themselves; do not describe
a broad ACCOUNT grant as a sort-key enforcement policy. Source transaction checks
and the invocation trust boundary remain necessary.

## Data lifecycle and activation blockers

The signed record is call-local and contains no raw email, correspondence, ID
documents or evidence payload. It remains an identity-linked capability. Neither
the adapter nor its package persists a new verification family, so no extra
backend verification table or export family is introduced. Disable gateway/body
tracing and redact capabilities from operator tooling. Existing deletion records
retain their original approved deadlines/suppression semantics.

The existing command is **not a durable support-origin/operator/proof audit**.
The independently controlled verification/support workflow must provide approved
audit custody, access controls, retention, deletion/export treatment and incident
handling. The existing informational 120-day deletion receipt policy cannot be
silently reused for that external case store. That workflow and its signer are
absent; this candidate cannot fulfill verified-email requests until they exist.

Before any activation, owner approval is required for actual ownership checks
(email-sender identity alone is insufficient), explicit-request verification and
freshness, capability expiry/revocation limits, verifier/operator separation,
external case/evidence retention and audit access. Then independently qualify the
KMS signer/Verify boundary, actual IAM HTTP event, direct-invoke denial, live resource
inventory/readiness/subject scopes and one disposable end-to-end request through
all twelve real receipts. Existing component evidence is reusable but does not
substitute for this new admission trust-boundary acceptance.

## Local validation

`/tmp/amt-live-deletion-venv/bin/python -m pytest tests/support_account_deletion -q`
uses real local RSA signatures plus Moto DynamoDB admission/CAS/replay. KMS transport,
Cognito and resource TableId/ARN metadata are injected; no AWS/IAM or actual human
verification qualification is claimed. The suite covers invalid signature/shape,
principal/audience/pin mismatch, expiry/clock/budget, original-operation replay,
profile/inventory races, lost acknowledgment and terminal recognition without
recreating identity. Existing account-data admission/service/HTTP suites validate
the shared import compatibility. Final source checks: 36 focused cases passed both
normally and with Python `-O` (pytest's standard optimized-mode warning retained);
41 existing admission/service/status cases and six subtests passed. Independent
review reran all 36 focused cases successfully. No cloud or signer-policy proof is
inferred from these results. Archive verification separately covers source equality,
compilation, disabled-before-SDK behavior and packaged synthetic admission/replay.
