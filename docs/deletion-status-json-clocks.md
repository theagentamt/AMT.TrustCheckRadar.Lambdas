# Persisted deletion status JSON clocks

The first designated Dev request was accepted with HTTP 202 and durably journaled. Its immediately following monitor ended with `HTTP_OBSERVATION_UNAVAILABLE`; the original helper did not retain the HTTP status/error code, so that observation alone cannot establish a specific HTTP failure or an erasure failure. No password reset or POST replay is part of this correction.

Source inspection and actual SDK/Moto handler reproduction identify a pending-status serialization defect: initial POST uses native integer command clocks, while GET or an exact replay reads DynamoDB `Decimal` clocks and passes them to plain JSON encoding. Both legitimate persisted cases returned 500 in the regression before the fix. The service now converts only the two clocks already validated as integral by `validate_command` to native integers. The wire schema, original operation, persisted rows, receipt validity, gates, retention and request idempotence do not change. Invalid fractional clocks still fail closed; the encoder does not globally coerce arbitrary numbers.

The monitor additionally records the numeric HTTP status and an allowlisted error code, never message/body/token values, so future unavailable observations can be diagnosed. It still records accepted state before polling, never retries POST, and requires same-poll dual denial before token expiry. This cannot recover the prior discarded token or retrospectively supply missing rejection evidence.

Validation: four new actual HTTP-handler/SDK/Moto cases cover GET and exact POST replay, valid native JSON timestamps and fractional-clock refusal, with no table mutation or transaction. They fail on the two valid persisted cases against the original source. Combined with eight admission cases, 12 SDK tests pass. Existing handler/service plus monitor tests pass 59 tests and 56 subtests. Deployment and any future independently designated synthetic qualification remain root-owned; the original account operation is unchanged.
