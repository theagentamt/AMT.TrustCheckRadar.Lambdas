# History terminal-fence and receipt replay candidate

Both History component receipt writers now read the exact current account-deletion fence before doing receipt work. A matching completed fixed fence causes a harmless skip, even after its informational 120-day receipt deadline. Missing, malformed, replaced or differently bound commands fail closed. A stale requested stream record cannot start a new History erasure job once the durable fence has completed.

The bridge's no-history/DELETED-state path and the lifecycle's completed-erasure path share one receipt helper. A new receipt is written in a transaction that checks every bound requested-command field and checks the History STATE proof (absent or DELETED for the bridge, DELETED for lifecycle). A concurrent terminal fence, changed operation or reappearing active History state cancels the write. Lost acknowledgments reread exact terminal or component evidence. Existing valid receipts are never rewritten with a later completion time or extended deadline; malformed or expired existing evidence is not silently replaced.

New receipts retain the existing 120-day period from their observed component completion time. The bridge previously anchored no-history evidence to request time; it now records the actual verified completion time consistently with other components. No new retention category, deletion-fence TTL or retirement mechanism is introduced. Fixed completed fences retain their existing conditional restore-suppression semantics.

The lifecycle validates a restored pending job's exact account/operation binding against the current fence before starting its next cleanup stage. A terminal match leaves the stale job unchanged and performs no receipt or replay-state recreation. This is not a claim that all restored jobs are retired or that every other History mutation is transactionally fenced: complete restore reconciliation, stale-job retirement and all-writer qualification remain acceptance work. The existing scan/scheduling fairness limitations are also unchanged by this bounded receipt fix.

Runtime remains inactive under existing gates (`HISTORY_ACCOUNT_DELETION_ENABLED=false` for the bridge and the existing lifecycle enablement gate). Infrastructure must supply scoped ledger GetItem, transaction-only requested-fence ConditionCheck and History receipt Put, plus transaction-only control-table USER# STATE ConditionCheck. No public mobile contract changes, deployment or identity removal are performed.

Validation uses synthetic actual-SDK/Moto cases for no-history completion, receipt retry timestamps, lost acknowledgments, terminal races in both writers and job creation, operation replacement, state reappearance, terminal replay beyond the receipt window, forged terminal binding and restored-job skip. Ordinary History tests retain prior non-account erasure behavior. These tests do not prove live IAM, restore/migration coverage or whole-account completion.
