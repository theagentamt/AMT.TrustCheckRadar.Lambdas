# Guarded automatic URL expansion

Owner decision October 31: automatic guarded expansion after explicit Check,
without a separate expansion option. QR decoding alone remains inert. The exact
reviewed disclosure is the only input: full links may expand; origin-only links
receive an origin reputation lookup without target GETs or withheld reconstruction.

The new consumer candidate.3 binds that profile and exact request intent to the
existing prepare/admit/settle proof. The private assessment schema2 coordinates
public DNS validation, Google lookup, then a private one-response schema2 fetch.
It repeats reputation before each next visit. The fetcher independently checks all
A/AAAA answers and pins a public IPv4 socket with original-host TLS verification.
It receives no Google credential or caller headers. Existing no-script, header,
request/hop/time bounds remain. No new IAM/network access or environment flags.

Five redirects / six fetches / six Google lookups, no retries; aggregate target
DNS/RPC time ten seconds within the existing consumer's eighteen-second assessment
budget. A lookup failure stops before the next target GET. A known match reports
high risk with limited coverage, including when no HTTP request was made to that
candidate. Incomplete or unsupported traversal never becomes clearance. The public
result has no destination/chain strings. GET can still register a visit or trigger
an action; Google receives disclosed candidate URLs. No-match is not a guarantee.
JS/meta/interactive navigation is outside supported HTTP-chain coverage.

One logical allowance operation: completed checks charge one where an allowance
applies, complimentary checks remain uncharged, partial/blocked/unavailable zero. Old candidate.1/.2 new submissions are rejected before refresh,
admission or provider work. Existing receipts still reconcile with original
versions, charges and evidence. Guarded requests never fall back to old protocols.
The old private schema1 profile remains for existing workers and is explicitly
outside this migration; do not claim all Message/recovery URL paths are migrated.

History read candidate.2 is selected by x-history-contract-version. It can return
unchanged legacy items and guarded candidate.2 stored items. Older readers fail
explicitly on a new item; no silent drop or projection downgrade. Cursors are
version-bound, retention/deletion/access rules unchanged. Concrete schemas and
synthetic fixtures live in contracts/url-consumer/1.0.0-candidate.3,
contracts/url-assessment/0.4.0-candidate.1 and
contracts/governed-history/1.0.0-candidate.2.

Compatibility limits requiring coordinated rollout: update Android URL and History
readers before creating new guarded receipts. Existing result-feedback versions
reject the new assessment version explicitly. Existing account-export versions
fail closed if a guarded summary is encountered; a separately versioned export
extension is required before enabling exports of these new receipts. No old
contract is silently widened. These are explicit remaining integration tasks,
not passing acceptance or changes to the user's accounting/access policy.

Direct source/package changes affect url_redirect_resolver, url_assessment,
url_consumer and governed_history, plus shared-authority/export validators used by
existing packages. Artifact publication, function deployment and alias activation
are separate gated actions. No deployment, credential, provider call, budget or
security-setting action is part of this local source candidate. Existing AI
qualification NO-GO and exhausted original defect attempts are unchanged.
