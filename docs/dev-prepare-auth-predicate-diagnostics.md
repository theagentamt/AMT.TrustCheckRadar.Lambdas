# Dev prepare authentication predicate diagnostics

This source-only change makes a rejected **late prepare account-JWT check** distinguishable using a fixed predicate code. It does not repair a demonstrated token, session or account defect, and it does not change any authentication check or HTTP response. Existing [ATCR-112](https://andmorethings.youtrack.cloud/issue/ATCR-112) and [ATCR-114](https://andmorethings.youtrack.cloud/issue/ATCR-114) remain open for their real Dev acceptance. Physical-only cases remain in [ATCR-148](https://andmorethings.youtrack.cloud/issue/ATCR-148). No duplicate issue, criterion waiver, deployment or reproduction is part of this source task.

## Retained observation and contract assessment

The closed 2026-10-17 03:40:30–03:43:30 UTC snapshots contained three access HTTP200s and one prepare HTTP401, with no observed verification/registration rows. Counts are aggregate and cannot identify an app request or actor. The prepare row recorded `$context.integration.status=401` with numeric integration latency. For Lambda proxy integrations, [AWS defines this field](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-logging-variables.html) as the status returned by the function code, unlike the Lambda-service invocation status. This supports an integrated backend response rather than a gateway-only preintegration rejection; it does not identify the failed JWT predicate.

The canonical Store13 source/public cached artifact uses `https://api-dev.andmorethings.net`; metadata resolved that custom-domain root to the expected API and prepare to `trustcheckradar-dev-v1-play-handoff:live`, version8 with CodeSha256 `riLQ3bwsUr95HPJyjCviZCqPfmloyoG515TjucsmjAY=`. All four protected route/integration fingerprints matched the approved baseline. An earlier end-of-string target checker falsely rejected the integration URI's `/invocations` suffix; the normalized function/qualifier check supersedes that checker result. The GET and prepare JWT authorizer IDs differ, but their type, identity source, JWT configuration and required scopes are equal. No routing defect was established.

The API JWT authorizer and the handler are distinct validation boundaries. API authorization is not a substitute for the handler's verified-context requirements: `requestContext.authorizer.jwt.claims`, a valid subject, exact configured `iss`, exact `client_id`, `token_use=access`, positive exact epoch `exp` strictly greater than server time, and the required scope string. The handler's narrower access-token checks are intentional; API audience acceptance alone does not imply that all handler predicates passed. The qualified issuer/audience/scope configuration presents no demonstrated static contract inconsistency that explains this response.

In the exact deployed source, prepare first invokes `require_engineering_subject`; its rejected engineering gate maps403. It then loads the authority and calls `Bindings.prepare` → `Authority._account` → the same `jwt_subject` parser. That later parser failure maps401 `AUTHENTICATION_REQUIRED`, with the original nonretryable response. Both parser callers obtain issuer/client/scope from the same environment and read the same unmutated request event. Their clocks are sampled separately around existing authority initialization work. Expiry between the checks is a source-compatible hypothesis, demonstrated only with synthetic fixtures. Actual token expiry, an ID-token path, wrong owner, invalid refresh credentials or an Android-specific cause has **not** been established.

Android's actual V1 GET and prepare paths share the owner-fenced Amplify access-token source. Its default session fetch may reuse valid cached credentials and refresh invalid/expired credentials; the legacy snapshot repository's forced-refresh option is not the actual V1 path. Neither Refresh balance nor owner re-login is a proven remedy. This change adds no forced refresh, token inspection, login/reset operation, POST replay, expiry grace or weaker admission.

## Implementation and privacy boundary

`shared_history.security.jwt_subject` retains the original extraction, `_exact_epoch` behavior, short-circuit order and conditional single `now()` sample. Its original `HistoryError` keeps the same class/code/message/details/retryable values. An internal attribute carries only the first failed fixed predicate, never a claim value. The diagnostic does not re-evaluate the rejected request against a later clock.

`Authority._account` retains the original caught exception set and raises the same `AUTHENTICATION_REQUIRED`. Its best-effort hook forwards only that internal fixed code to `shared_check_authority.prepare_auth_diagnostics`; missing/unclassified internal codes become `UNKNOWN`. Hook import, attribute or logging failures are suppressed and cannot change authentication, account-store work, provider calls, response mapping or retry policy. Unrelated handlers do not emit the new event.

The logger requires **all** existing conditions: exact `STAGE=dev`, `PLAY_PREPARATION_ENABLED=true`, `AUTHORITY_ENABLED=true`, payload version2.0, exact POST `/v1/purchases/google-play/prepare`, and POST HTTP context. It is silent for UAT/Production, disabled gates, malformed context, GET access and POST verify. Preparation remains independent of verification activation; this does not add a new flag or enable either route.

The complete emitted shape is:

```json
{"event":"dev_play_prepare_auth_failure","schemaVersion":1,"stage":"AUTHORITY_ACCOUNT_JWT","predicate":"EXPIRY_NOT_FUTURE"}
```

Allowed predicates: `CLAIMS_UNAVAILABLE`, `SUBJECT_INVALID`, `ISSUER_MISMATCH`, `CLIENT_MISMATCH`, `TOKEN_USE_MISMATCH`, `EXPIRY_INVALID`, `EXPIRY_NOT_FUTURE`, `SCOPE_MISSING`, `UNKNOWN`. No decoded claim values, account/subject identifiers, request IDs, tokens, proof, headers/body, payload, exception text/traceback, expiry timestamps or provider responses enter the event. Untrusted predicate inputs become the fixed sentinel. The logger consumes no claims or exception object and performs no SDK or network operation. The existing application validator still necessarily examines its already verified JWT context in memory.
