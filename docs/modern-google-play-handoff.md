# Modern Google Play handoff — SECUR4ALL-195 candidate

This source increment connects verified Play proof to the modern shared allowance authority. It preserves the retired purchase handler and its deny boundary. It does not activate checkout, a paid grant, acknowledgment, background lifecycle processing or a production release.

## Current provider evidence

The owner confirmed the existing package `com.andmorethings.trustcheckradar`; product `trustcheck_radar_pro_monthly`, base plan `pro-monthly` remain the intended monthly configuration. A read-only catalog audit using the existing AWSCURRENT credential found valid credential format and successful OAuth authentication, but catalog GET returned HTTP403 / PERMISSION_DENIED / SERVICE_DISABLED. The Android Publisher API must be enabled in Google project `trustcheck-radar`. Product/base-plan state, P1M duration, US price, tester enrollment, test build/track availability, order/verification/ack permissions and RTDN are not yet verified. No customer purchases/orders or store mutations were accessed in that audit.

## Verified proof and transaction boundaries

- A new candidate `POST /v1/purchases/google-play/verify` uses JWT account, current active device, profile/age, durable deletion and engineering allowlist gates. Server catalog configuration is authoritative. Native request schema contains only version, UUID, PURCHASE/RESTORE intent and token.
- Read-only lineage discovery precedes an exact ownership/inventory observation. The complete same lineage is then freshly verified, up to eight tokens, with a fixed-host bounded client and a 20-second request deadline. No provider response or token is logged.
- Current subscription state and its line item's `latestSuccessfulOrderId` select an exact Orders API record. Order token/product/base plan and processed state must match. The funded order's service-period dates supply accounting dates; original subscription `startTime` does not supply a renewal period. Only the reviewed monthly base-price plan is supported initially. [Subscription resource](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptionsv2), [Order resource](https://developers.google.com/android-publisher/api-ref/rest/v3/orders).
- Google distinguishes current access expiry from funded accounting period end. This first candidate rejects differing dates, including unsupported grace/deferral extensions, and rejects unsupported replacement/out-of-app/offer forms; it never creates a fresh 200-check allowance from an extended expiry. Pending or inactive submitted old tokens do not revoke a newer linked subscription. Background authoritative lifecycle is still SECUR4ALL-125/244 acceptance. [Lifecycle guidance](https://developer.android.com/google/play/billing/lifecycle/subscriptions).
- Ownership/lineage locators, immutable funded usage, account PERIOD, ACCESS and request audit commit in one conditional DynamoDB transaction. Pre-provider ACCESS/device/ownership/inventory changes invalidate the proof for writing; conflict requires fresh verification. Existing counters are preserved, not replaced from a store response.
- Acknowledgment occurs only after durable request evidence and fresh account/device/ownership/paid-source checks. An acknowledgment failure preserves the committed grant and returns pending acknowledgment. Retries verify again without replenishing the period. If an uncertain request survives renewal, exact historical request evidence plus freshly acknowledged, still-owned lineage can return an acknowledged replay without granting or acknowledging the new period. Android may then perform one fresh correlated verification; counters still derive from the immutable funded ledger. No raw token is retained for a new background queue; foreground interruption recovery and RTDN/polling reconciliation must be qualified before paid launch. A store acknowledgment cannot be atomic with AWS deletion; no acknowledgment result can recreate a deleted account or write an unfenced grant. [Google security guidance](https://developer.android.com/google/play/billing/security), [acknowledge API](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptions/acknowledge).

## Approved minimal purchase-period retention

The owner approved preserving remaining purchased checks after account deletion and restoration. One minimized purchase-linked usage record is retained until the immutable funded period ends plus 604800 seconds. It contains only purpose/version metadata, hashed purchase/order identity, funded dates, the 200-check limit and completed/reserved counts, plus exact expiry/index metadata. It contains no account ID, message, URL, token, raw order ID or provider response. Historical backup copies may remain for up to 35 additional days under the disclosed existing backup window.

Global key: `PK=V1#PURCHASE_USAGE#SHA256(store + NUL + stable subscription identity)`, `SK=PERIOD#SHA256(funded order identity)`. Play identities passed here are already token/order SHA256 digests. The non-account key survives account partition erasure. Existing account PERIOD and admitted CHECK records carry its pointer and remain subject to account deletion; existing ownership and authority-audit retention remains account lifetime, not an additional indefinite deleted-account binding.

Admission and complete-only settlement update the account and purchase-period counters atomically. Partial/failed/inconclusive work and technical retry never add a completed charge. Lease cleanup and account erasure release pending reservations without erasing completed usage. Restore requires fresh store proof, no other active ownership, and preserves the existing global counters. Missing/unrecognized legacy accounting is a reconciliation error, not a fresh allowance. A new funded period receives its own 200-check limit; the previous period is never rewritten to reset usage.

Logical expiry is enforced separately from asynchronous DynamoDB TTL. The explicit expiry worker handles the global record at its fixed deadline. No code claims immediate physical removal from backups. Restore and paid admission require coordinated deployment/inventory qualification of every URL/message/recovery/settlement/deletion worker; an old writer without the paired ledger cannot remain active.

## Infrastructure and activation

Artifact `v1_play_handoff.zip`, Python 3.14/arm64, handler `v1_play_handoff.app.lambda_handler`. Provisioning must keep `PLAY_HANDOFF_ENABLED=false`, `AUTHORITY_ENABLED=false`, `PLAY_CATALOG_P1M_VERIFIED=false`, empty subject allowlist and existing consumers/schedules closed. Dev requires `PLAY_REQUIRE_TEST_PURCHASES=true`; non-test proof cannot grant or acknowledge. Real purchases are not enabled by a test-candidate deployment.

Existing authority table and two exact existing Secrets Manager ARNs are reused; no new secret value or table is introduced. Secrets reads explicitly select AWSCURRENT. Handoff uses GetItem and native transactional Put/ConditionCheck only; it cannot debit checks, scan users, invoke analysis providers or mutate the retired legacy entitlement shape. Shared usage workers retain their narrowly reviewed transactional Update/Delete and expiry-index permissions. Gateway throttles and protected inventory are required before activation.

The public contract is immutably pinned at `a2a2e9e9235997e66c0daede428b640ad578c6b9`, `contracts/v1-play-handoff/candidate.1`. Responses report historical handoff/acknowledgment status and require a fresh authoritative access snapshot. Android must never acknowledge from this modern flow, infer entitlement from the handoff response or convert automatic foreground reconciliation into a cross-account restore.

## Remaining acceptance

SECUR4ALL-195 remains open until the coordinated source and deployments, real test catalog/proof/order/ack protocol, race/retry/deletion/restore cases and native test build are qualified. SECUR4ALL-125 background renew/refund/revocation and SECUR4ALL-244 authenticated ingress are paid-launch requirements. Unknown store state is never treated as a fresh grant. No fixture or closed-handler smoke substitutes for actual Google license-test evidence or customer activation approval.
