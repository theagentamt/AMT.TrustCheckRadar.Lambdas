# Independent research consent 2.0.0-candidate.2

GET and PUT `/v1/users/campaign-participation`, authenticated owner, JSON, no subscription or allowance requirement. GET optionally accepts exactly `operationId=<UUIDv4>` to reconcile an owned operation. Every successful response is HTTP 200 with the exact response fields in the schema. No quota, free-check, credit, entitlement or usage fields are returned or changed.

PUT fields: `schemaVersion` integer1 or2, `action` join/withdraw, `noticeVersion` nonempty UTF-8 string up to64bytes, and `operationId` canonical UUIDv4. Schema2 additionally requires `expectedStateVersion`, an integer0..9007199254740991 from the reviewed state; schema1 must omit it. No other fields are accepted. New Join requires schema2 and the current notice. Schema1 Join is replay-only: an existing matching schema1 receipt may be reported; absence returns POLICY_REVIEW_REQUIRED and never performs Join. New Join is gated by CONSENT_INDEPENDENCE_ENABLED=false by default. Reads, reconciliation and authenticated withdrawal continue while new Join is gated. Withdrawal never requires acceptance of the new notice.

Current state and operation evidence are independent. An old Join operation can be applied while today's state is review_required, withdrawn or withdrawal_pending. Never infer operation success from current state alone. The operation UUID, action, request schema and request notice identify a new immutable request. Reuse with different fields returns CONFLICT. Legacy recordVersion1 evidence knows schema1/action/UUID but did not store request or accepted notice: requestNoticeVersion and acceptedNoticeVersion are null. A schema2 mutation cannot reuse that old UUID. GET can display applied_legacy without claiming new consent. not_found has all fields except operationId/status null; it is unresolved evidence, not proof a request never executed (receipt retention is bounded).

Exact operation lookup honors its logical expiresAt even while asynchronous DynamoDB TTL still retains the row. No expired receipt is renewed by a retry.

Stored old enrollment is projected as review_required until explicit current Join creates a fresh epoch. It does not widen old receipts or permission. A legacy pending withdrawal remains pending. A legacy withdrawn row is completion_unverified: no whole-account or research erasure promise. deletionDeadlineAt is the original requested deadline, not proof of physical erasure. An old persisted operation without owner binding must never be replayed under a newly authenticated account. Canceling a local operation does not withdraw research.

Consent/operation receipts keep their original 400-day expiry; new ones have 400 days from operation acceptance. Participation state remains account-lifetime. No extra migration store or rewritten historical records. Separate commercial/demographic permission is not granted. Campaign processing must remain disabled until all publisher/cluster eligibility and withdrawal fences are qualified; GET projection alone does not stop old workers.

Errors: exact `{"error":{"code":...,"message":...,"retryable":boolean}}`, optional `details` list of field/issue. INVALID_REQUEST=400, UNAUTHORIZED=401, FORBIDDEN=403, NOT_FOUND=404, CONFLICT/POLICY_REVIEW_REQUIRED=409, JOIN_UNAVAILABLE=503, SERVER_UNAVAILABLE/INTERNAL_ERROR=500. Unexpected failures use fixed messages, no customer payloads. Conflict may be retryable but a client must reconcile the same immutable operation before deliberate retry; never silently change notice, account or operation UUID.

A reviewed new Join creates a new consent epoch; it does not erase or reauthorize old-epoch source rows. Old-epoch outbox/feature/locator/repair inventory and any pending withdrawal remain separate cleanup obligations. Rollout cannot infer historical cleanup from a new epoch or an enrolled response.

Schema2 mutations require expectedStateVersion (the exact state revision reviewed by the user). The server checks this before changing consent and stores it with operation identity; reusing an operation UUID with a different expected revision conflicts. Existing exact applied-operation replay is resolved before comparing current state. Schema1 omits this field, stays Join-replay-only, and may still withdraw; operation expectedStateVersion is null for schema1 and missing lookup. A delayed first Join from before another-device withdrawal therefore cannot silently enroll again.
