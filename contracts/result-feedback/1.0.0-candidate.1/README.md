# Private result feedback candidate 1

Approved policy and exact interface copy are pinned in policy.json/messages.json. This contract does not authorize deployment. Only POST `/v1/result-feedback` is supported, with bounded4096UTF8-byte JSON and no extra fields. Body account ownership, content, URLs, verdict overrides, free text, research IDs and arbitrary fields are forbidden. Account comes from verified JWT context; active-device and deletion fences are required. Subscription/allowance does not gate feedback and no analysis check is consumed.

`feedbackId` is opaque1–64ASCII `[A-Za-z0-9_-]`, normally a random UUID/128-bit ID generated once. It is scoped to the exact owned CHECK result, **not globally unique across the account**. No digest protocol is used. The result reference binds checkId, operationProof, receiptId and supported assessmentTransportVersion. Server authorization verifies all four against a retained owned settled row; a client ID or digest is never evidence of ownership. The admission deadline in operationProof may have passed; it remains usable for this operation while the original settled receipt is retained and cryptographically valid.

Eligibility requires explicit full_url/origin_only URL scope or sanitized_message scope, a valid nonnull stored summary with exact check/version, and displayed processingOutcome complete, partial or inconclusive. The current URL private contract supports eligible complete/partial only; message supports all three. Canonical URL mapping must also yield an eligible assessment, not a technical error relabeled from a retained partial summary. Noncharged partial/inconclusive assessments qualify. Technical-only failed/invalid_input/unsupported/blocked/unavailable outcomes do not qualify. Neither a local/history/legacy/recovery result nor pending/unknown/no-summary/expired/corrupt references qualify. Clients must bind the actual displayed assessment to that receipt; never attach a preserved older threat finding to a newer contradictory/failed result. See eligibility.json; each positive matrix entry still requires all stated prerequisites and the family-specific summary validator.

The four category values are user opinions for private product quality. No result, allowance, provider, campaign or research consent state changes. No human response or support ticket is promised.

Acknowledgment semantics:
- accepted: exact first report committed, or exact same feedbackId/category on this result confirmed again under current account/device/deletion/expiry transaction fences. Returns original server receivedAt and existing result expiresAt.
- already_received: a different feedbackId targeted an already-reported result. No additional choice was stored, and earlier category is never returned. Returns original receivedAt and expiresAt but echoes the current request feedbackId/checkId for correlation. Use the distinct approved already-received message.
- rejected: fixed reason; not an acknowledgment. Same feedbackId with changed category is FEEDBACK_ID_CONFLICT. That ID may independently be used on another owned CHECK because idempotency is result-scoped.
- unknown: unavailable/uncertain delivery. No receivedAt/expiry is asserted. Explicit same-report retry is allowed only when retryable=true. Never infer failure or cancellation of a possible committed report from a timeout.

Epoch times are integral UTC seconds. On accepted/already_received, `0 <= receivedAt < expiresAt` is a required cross-field invariant. All other states have null times. HTTP200 covers accepted/already_received;401 authentication;403 account/device;404 non-disclosing result-unavailable;409 changed-category conflict;422 bad input/contract;429 bounded authenticated attempt limit;503 disabled/unavailable. RATE_LIMITED has retryable=true and1–86400retryAfterSeconds. SERVICE_UNAVAILABLE has retryable=true and null retry delay; SERVICE_NOT_ENABLED is nonretryable until service configuration changes. No automatic retries/outbox. Clear transient form on background/account/result changes and ignore stale responses without claiming remote cancellation.

Store one bounded `{feedbackId,category,receivedAt,policyVersion}` object on the CHECK row. Same receipt TTL/index/summary/accounting values remain untouched. Feedback becomes inaccessible at the original seven-day receipt deadline, not seven days after submission. Existing explicit expiry and account deletion remove the complete row; TTL is delayed fallback. Shared-table PITR/historical copies can outlive active expiry. Effective backup/copy settings must be verified before activation; restored data stays quarantined until expiry/deletion fences are reapplied. No longer-lived extract/aggregate or complete account-export claim is implied.

Fixtures are synthetic protocol cases, not live acceptance. English/Spanish wording matches the owner-reviewed copy. Client format checks and in-memory duplicate suppression supplement, never replace, server ownership, bounds and deletion-race controls.
